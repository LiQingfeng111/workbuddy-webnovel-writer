# 写章闭环

一章从「准备写」到「定稿入档」共七步。次序不可颠倒，尤其不可跳过第 6 步的作者裁决。每一步都有明确的输入与落盘产物；模型在对话里说一句「完成」不构成任何一步的完成证据。

---

## 第 1 步 · 状态校准

```bash
python -X utf8 scripts/novel.py status --root <书仓根>
```

从磁盘读取：最后定稿章号、当前草稿及其稿次、未回收伏笔数、累计汉字数、契约篇幅、下一章细纲是否已备。

向作者如实报告这些事实，并说明建议的下一步。禁止用聊天历史推断进度；`state.json` 与文件冲突时以文件为准（必要时 `rebuild`）。

**分支**：
- 无书仓 → 转 `01-立项与契约.md`。
- 当前章已有草稿 → 从草稿所处环节继续，不重写已完成的正文或审读。
- 用户明确说「开新章」→ 核对上一章确已定稿、账本已沉淀，再进入第 2 步。

## 第 2 步 · 确认细纲

读 `02-大纲/卷NN.md` 中本章条目，逐项核对：POV、场景、出场人物、承接前章、必写事实、伏笔动作、预计字数。

细纲缺失或与前章不连贯时，先补细纲并**请作者确认**。禁止边写边临时编造本章目标。

## 第 3 步 · 写作备料

组装一份自包含的备料清单，只放本章真正用得上的内容：

1. `00-契约.md` 的读者承诺、禁区、篇幅约定；
2. 本章出场人物的人物卡（尤其「语言习惯」「禁止写法」「当前状态」）；
3. 相关地点、势力、能力规则（原文引用，不转述成模糊摘要）；
4. 前 1–3 章的章摘要与末尾 300–500 字（承接语气与未闭合动作）；
5. `05-账本/伏笔台账.md` 中与本章有关的未回收条目；
6. `05-账本/事实账本.md` 中会影响本章的事实（时间、伤势、物品归属、人物知情范围）；
7. `05-账本/本书记忆.md` 中作者明确过的写法偏好。

用 `query --term <关键词>` 全文检索辅助定位，报告中附文件路径与行号。备料不足时如实标「材料待核对」，不要靠常识补全设定，更不要编造前文没发生过的事。

## 第 4 步 · 正文起草

```bash
python -X utf8 scripts/novel.py draft --chapter 12 --title 第十分钟 --root <书仓根>
python -X utf8 scripts/novel.py count --root <书仓根> --file <草稿路径>
```

草稿写在 `04-草稿区/第012章/稿N.md`，带 frontmatter（章号、章名、稿次、状态、细纲版本、创建时间）。写作要求：

- 严格按细纲交付本章目标、必写事实与伏笔动作；
- 遵守人物语言习惯与禁止写法；
- 以契约的「目标汉字数」为写作目标，允许在自然情节节点先保存暂存稿再核字数；
- 越界时最多自行调整一轮并另存新稿（稿2、稿3…），仍越界则如实交接，不反复裁剪；
- 不在正文里写「前面提到过」这类面向作者的说明，不做总结式收尾。

`count` 的汉字数口径：正文含章标题，排除 YAML frontmatter 与 HTML 注释。报告时必须标明口径，另报字符数须单独标注。

## 第 5 步 · 八维审读

```bash
python -X utf8 scripts/novel.py check --root <书仓根> --chapter 12 --json
```

先看脚本的确定性发现项（篇幅、章号、占位符、frontmatter、伏笔登记），再按 `04-八维审读.md` 逐维做语义审读，写到 `04-草稿区/第012章/审读报告.md`。

规则：
- 每条发现项必须有原文证据（引用片段 + 位置）与可执行建议；
- 脚本没跑、或跑的是旧稿，就不能声称确定性检查通过；
- 换稿、细纲升版、材料刷新后，旧结论全部作废，按当前稿重跑；
- 不伪造「零发现项」，也不把模型自己的判断写成脚本输出。

## 第 6 步 · 作者裁决

向作者完整呈报，然后**停下等待**：

```markdown
## 第 12 章 · 待裁决
- 待审稿: 04-草稿区/第012章/稿2.md
- 正文汉字数: 2031（目标 2000，区间 1600–2400）；字符数口径另计
- 确定性检查: 通过 / 3 项发现（附编号）
- 八维审读: 维度 → 发现项条数 → 严重度最高项
- 待沉淀事实候选: …（时间线 / 账本 / 人物状态 / 本书记忆）
- 需要作者决定: ① 发现项 D-03 是否保留 ② 是否批准定稿
```

处置方式三选一：**修改**（回第 4 步另存新稿）、**作者保留**（记录理由，发现项保留在报告中）、**忽略**（仅适用于明显误报，须写明理由）。

未经明确确认，不得执行 `settle`，不得把候选事实写进账本，不得把草稿复制进正文。取消、沉默、迟到的回复都不算授权。

## 第 7 步 · 定稿沉淀

```bash
python -X utf8 scripts/novel.py settle --root <书仓根> --chapter 12 --title 第十分钟 --confirm "作者已确认定稿"
python -X utf8 scripts/novel.py status --root <书仓根>
```

`settle` 只负责确定性的原子入档（校验 → 临时文件 → 替换 → 重建派生状态）。语义沉淀由模型在同一轮完成，按 `05-事实沉淀与断更恢复.md` 更新四本账：

1. `事实账本.md`：本章发生的、会约束未来的事实；
2. `伏笔台账.md`：埋设 / 推进 / 回收，带章号；
3. `人物状态.md`：出场人物的章末快照；
4. `本书记忆.md`：作者本书层面的决定与有效写法（去重后新增）。

入档后停止在边界，不自动开下一章。核对 `status` 输出与账本一致；若 Git 可用，建议作者提交一次（`ch: 第012章 定稿`），提交失败不重复入档。

---

## 中断与恢复

| 中断点 | 恢复方式 |
| --- | --- |
| 起草中 | 保留暂存稿，重新 `count` 后继续写，不覆盖 |
| 审读中 | 核对当前稿指纹是否变化，变了就重跑 |
| 等待裁决 | 重新呈报，不视为已批准 |
| 入档失败 | 查临时文件与正文是否完整，修复后重试，不重复升版 |
| 换会话 / 断更数月 | 只说「继续」，从 `status` 与文件重新校准 |

暂停期间不要手工修改同章文件；外部编辑器改动后，回来先 `status` 与 `query` 核对差异，按影响分析处理。
